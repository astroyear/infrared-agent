# 开发设计文档

> 状态：待审阅。本轮只确定设计，不开始业务代码开发。
> 本文以《项目实施规划》为依据，面向个人项目的首版实现。优先把检测、问答和知识管理做成完整闭环，不引入暂时用不到的系统。

## 1. 已确定的设计

| 项目 | 首版方案 |
| --- | --- |
| 部署 | WSL Docker，frontend、backend、db 三个容器 |
| 后端 | 一套 Python 3.11 环境，FastAPI、LangGraph、LangChain、PWL-RTDETR |
| 前端 | 建议 Vue 3 + TypeScript + Vite，Nginx 提供页面并代理 API |
| 数据库 | PostgreSQL + pgvector |
| 登录 | 用户名和密码登录，签发 JWT |
| 密码存储 | 按项目要求明文保存，用于个人演示 |
| 用户权限 | 不分管理员角色，所有登录用户均可维护公共知识库 |
| 数据隔离 | 图片、检测任务、聊天和偏好属于各自用户 |
| ID | UUID v4 |
| 图片存储 | 后端文件目录 + Docker 持久卷，每次检测独立目录 |
| 知识文件 | Markdown（.md） |
| 大模型 | 外部 LLM 和 Embedding API，提供商待确定 |

现有 Python 3.11 环境已完成单张模型预测，保留 wtconv2d.py 的兼容修复。新增依赖后的模型回归及 Linux 容器验证仍需执行。

## 2. 用户使用流程

用户先注册并登录，进入以下三个功能页：

1. **图片检测**：上传图片，点击检测，查看原图、结果图和目标列表。
2. **智能问答**：提问论文或模型知识、附图请求检测、追问已有检测结果。
3. **知识管理**：上传资料，查看公共文档；通过管理 Agent 新增知识或提出更新，确认后覆盖。

所有登录用户可以操作同一公共知识库。某人新增的文档，其他人可以查询并提出更新；但不能读取别人的图片、聊天或确认别人的待办操作。

首版不做角色权限后台、刷新令牌、邮箱验证、找回密码、视频检测、PDF/OCR、独立任务队列和本地大模型服务。

## 3. 注册登录：只使用 JWT

### 3.1 处理过程

注册时，后端检查用户名是否重复，将用户名和密码写入 users 表。用户名去除两端空格并采用统一大小写规则；密码按用户输入原样保存和比较，不做静默截断。

登录时，后端查询用户并比较密码，成功后签发 JWT，返回 access_token、token_type、expires_in 和用户公开信息。密码不出现在用户信息响应或日志中。

JWT 至少包含：

- sub：用户 UUID 字符串。
- iat：签发时间。
- exp：过期时间。

建议初始有效期为 24 小时，通过配置调整。使用成熟 JWT 库，服务端固定允许的签名算法，密钥从环境变量读取；不接受客户端指定验证算法。

前端建议将令牌放在 sessionStorage，所有业务请求携带：

```http
Authorization: Bearer <access_token>
```

后端统一验证签名、过期时间和用户是否存在，得到 current_user。缺失、无效或过期令牌返回 401，前端清除登录状态并跳回登录页。

退出只在前端删除令牌和用户缓存，不提供服务端 logout 接口，不建立 auth_sessions 表，也不设计 Cookie 会话和 CSRF Token。已签发令牌退出后仍有效直到过期；首版接受这个行为，不宣称退出会立即撤销令牌。

### 3.2 明文密码的项目边界

明文保存是本项目明确选择，数据库或备份的读取者可以直接看到密码。因此仅使用不与其他账号重复的测试密码；如将来转为真实用户或公开服务，应先迁移为密码哈希。此处不额外实现密码哈希机制。

JWT 签名密钥不是用户密码，应独立设置且不提交 Git。密码和令牌不写进日志；前端令牌存储可被页面脚本读取，因此展示聊天和文档内容时不能直接执行其中的 HTML/脚本。

## 4. 后端如何组织

### 上传文件约定

首版只接受两种用途的文件：

| purpose | 接受格式 | 用途与可见范围 |
| --- | --- | --- |
| image | .jpg、.jpeg、.png，且能解码为 JPEG/PNG | 仅用于检测，原图和结果属于上传用户，不写入知识库 |
| knowledge | .md，UTF-8 文本 | 先保存为上传者的待入库文件，入库后成为公共知识文档 |

图片接口拒绝 Markdown，知识入库拒绝图片和 TXT/PDF/Word。聊天中的 attachment_ids 只是这两类文件的引用，不表示支持任意格式附件。上传 Markdown 不等于同意覆盖：先查重与比较，再决定新增、复用或等待确认。

后端验证扩展名、实际解码结果和用途，不仅信任 Content-Type。Markdown 以文本处理，前端渲染禁用或清洗原始 HTML，不执行其中脚本。

### 模块结构

```text
backend/app/
├── main.py                   FastAPI 入口和生命周期
├── core/                     配置、数据库连接、JWT 验证、日志
├── api/                      auth、files、detections、chat、documents
├── schemas/                  请求和响应模型
├── models/                   SQLAlchemy 业务表
├── services/
│   ├── detector.py           加载 PWL-RTDETR、预测、绘图
│   ├── detection_service.py  检测任务与结果保存
│   ├── storage.py            文件读写
│   ├── knowledge_service.py  入库、版本和变更确认
│   └── retrieval.py          检索
├── agents/                   问答 Agent、知识管理 Agent
├── tools/                    Agent 工具
└── graph/                    State、节点、路由、图构建
```

调用方向统一为 API/图节点/工具 → 业务服务 → 数据库或模型。首版不为了分层额外建立大量空接口；公共逻辑抽到服务中，避免聊天和按钮操作各写一套实现。

模型源码继续保留在 RTDETR-main-code。后端启动时确认导入本地自定义 ultralytics，不能被官方同名包替代。服务通过配置定位源码和权重，不依赖启动终端的当前目录。

FastAPI 启动时建立数据库连接池、加载检测模型、初始化模型 API 客户端、两个 Agent 和 LangGraph。每次请求复用，关闭时释放资源。首版一个 Uvicorn worker，避免重复加载模型。

## 5. 图片检测的完整实现

### 5.1 输入与目录

检测页可以直接上传文件；聊天中先上传附件取得 file_id，再根据用户请求创建检测任务。两种入口调用同一个 DetectionService。

后端先验证图片，再生成任务 UUID，目录为：

```text
/app/storage/detections/<task_id>/
├── input.jpg 或 input.png
├── result.jpg
└── result.json
```

建议首版限制 JPEG/PNG、10 MiB、2000 万像素，限制值可配置。验证真实解码结果，不仅看文件扩展名。文件名由后端生成，原始文件名只作为元数据保存。

已有聊天附件复制到任务目录，保证以后删除附件不破坏检测输入。模型只预测 input 文件，不对整个目录进行扫描。

### 5.2 模型与输出

Detector 提供 load 和 predict 两个主要方法，负责模型计算，不负责用户权限或数据库操作。

默认 device=cpu、imgsz=640、conf=0.25。客户端首版只调整 conf。沿用现有 RT-DETR 的预处理和后处理，不重写坐标换算。

调用 model.predict 时设置 save=False，由业务层调用结果绘图能力保存 result.jpg，并从同一结果对象生成数据库记录和 result.json。注意 OpenCV 与前端图片处理中的 BGR/RGB 约定。

结果包含任务 ID、状态、图像宽高、模型哈希、参数、原图 URL、结果图 URL 和 detections。每个目标包含 class_id、class_name、confidence、bbox_xyxy；坐标对应原图像素。类别从 model.names 读取。没有框仍算成功。

### 5.3 状态、并发与失败

任务状态为 pending、running、succeeded、failed、interrupted。

CPU 推理放入受控线程，并用锁限制同时一个预测，避免阻塞 FastAPI 事件循环或并发修改模型状态。首版等待时间设上限，服务繁忙时明确返回，不无限排队。

正常请求等待结果返回；如果等待超时而任务已开始，返回 202 和任务 ID，前端查询状态。线程不会因 HTTP 超时自动终止，任务服务继续管理它，退出前不能提前释放推理锁。

结果先写临时文件，再替换为正式文件，最后提交数据库成功状态。进程重启后识别遗留 running 任务并标为 interrupted；首版允许重新提交，不做自动续算。

用户主动重测创建新 UUID。网络重试使用幂等键：相同用户、相同键和参数复用任务，不重复推理；相同键但内容不同返回冲突。

### 5.4 前端如何显示私有图片

图片接口验证 JWT 和任务归属，然后用 FileResponse 返回文件。普通 img 标签不会自动添加 Authorization 请求头，因此前端通过带 JWT 的 fetch 获取 Blob，再生成对象 URL 显示；页面切换时释放对象 URL。

不把 JWT 放在图片 URL 中，不直接公开整个存储目录。数据库保存相对存储键，不返回服务器绝对路径。

## 6. 知识问答与知识管理

### 6.1 公共知识入库

Markdown 上传后先成为“待入库文件”，仅上传者可访问，不立即进入检索范围。用户明确要求新增或确认更新后，执行：

读取 Markdown（.md） → 规范化 → 内容哈希查重 → 分块 → Embedding → 保存版本和向量 → 发布有效版本。

首版支持 UTF-8 文本。分块先按标题和段落，长度和重叠作为可配置参数，通过问答评测调整。每块保存标题、版本和原文定位。

公共知识在全站范围查重和检索，不按上传者过滤。文档创建人、版本提交人用于追溯，不作为知识库访问门槛。发布时建立独立的公共版本文件引用，不将上传者的检测图片或其他待入库文件公开。

Embedding 在长事务之外完成，准备好后用短事务提交版本。失败不切换有效版本。模型和向量维度固定，换 Embedding 模型时重新建立对应向量数据。

### 6.2 问答 Agent

首版提供两个工具：

| 工具 | 行为 |
| --- | --- |
| search_knowledge | 搜索公共知识有效版本，返回片段和来源 |
| get_detection_result | 查询当前用户的指定检测任务 |

回答附可核验引用。资料不足允许有限次数检索改写，仍不足则说明。建议初始最多 3 轮检索、6 次工具调用，后续依据实际效果调整。

纯文本 LLM 可以解释数量、类别和置信度，不能声称看懂原图或确定漏检原因。检索文档中的文字是资料，不是新的系统指令。

先实现向量检索，之后增加中文 BM25 和 RRF，使用同一问题集对比命中率、引用正确率和延迟，不先堆叠检索组件。

### 6.3 知识管理 Agent

工具包括搜索文档、读取版本、提出变更、执行已确认变更、验证检索。

用户 A 新增的公共文档，用户 B 可以提出更新，无需管理员角色。覆盖仍按以下流程：

查找旧版本 → 比较内容 → 保存变更提议 → 展示差异 → 发起人确认 → 校验旧版本 → 入库并切换 → 验证。

待确认操作属于发起人的会话，只有发起人能确认或取消。其他人可以新建自己的变更。记录预期旧版本、新内容哈希和确认状态；确认时旧版本变化则返回冲突，重新比较。

执行工具必须查询真实确认记录，不能相信 Agent 自报“用户已确认”。重复确认或图恢复时复用已生成的版本，避免重复覆盖。

## 7. LangGraph 状态与会话

外层图负责路由和协调，两个 Agent 负责使用各自工具。

| 请求 | 路由 |
| --- | --- |
| 检测页按钮 | 直接检测，不调用意图分类 |
| 聊天要求检测并有图 | 检测节点 |
| 检测但缺图 | 澄清节点 |
| 模型或论文问题 | 问答 Agent |
| 追问上次结果 | 问答 Agent 查询本人检测记录 |
| 新增或更新知识 | 管理 Agent |

State 保存 messages、intent、attachment_ids、last_detection_task_id、evidence_refs、pending_operation_id 和 error。每轮清空本轮临时字段，保留必要的任务引用和未完成操作。

thread_id 使用会话 UUID 字符串，同一会话重复使用；后端先检查会话归属，再读取检查点。同一 thread 的请求顺序处理。

PostgreSQL checkpointer 保存执行状态，PostgresStore 保存用户明确确认的偏好，按 user_id 命名空间隔离。用户身份通过可信上下文注入，不能由 LLM 或请求正文任意指定。

确认暂停和恢复使用 LangGraph 相应机制，实施时验证父图与 Agent 子图配置。所有有副作用的操作仍需业务幂等，不假定配置检查点就一定不会重放。

## 8. 数据库设计

业务表使用 UUID 主键及 created_at/updated_at。私有资源记录 owner_id；公共知识记录 created_by 等追溯字段。首版不设角色表、权限表或登录会话表。

| 表 | 主要字段 | 用途 |
| --- | --- | --- |
| users | username、password | 用户名唯一，password 按要求明文保存 |
| files | owner_id、visibility、purpose、original_name、media_type、size_bytes、sha256、storage_key | 检测图片、待入库 Markdown 和已入库公共文档的文件记录 |
| detection_tasks | owner_id、input_file_id、output_file_id、status、parameters、model_hash、result_json、error_code、idempotency_key、request_hash | 检测任务及结果 |
| conversations | owner_id、title | 聊天会话，id 对应 thread_id |
| chat_messages | conversation_id、role、content、client_message_id、result_refs | 前端可见历史，role 指消息类型而非用户权限 |
| documents | title、source、active_version_id、created_by、updated_by | 公共文档 |
| document_versions | document_id、version_no、file_id、created_by、content_hash、status、embedding_model | 文档版本 |
| chunks | version_id、ordinal、text、location、embedding | 检索片段 |
| knowledge_operations | owner_id、thread_id、document_id、expected_version_id、candidate_file_id、content_hash、status、result_version_id | 提议、确认和执行记录 |

关键唯一约束：用户名、用户内非空检测幂等键、会话内 client_message_id、文档内版本号、版本内分块序号。向量维度在选择 Embedding 后确定。

LangGraph 检查点和 Store 使用组件管理的表。chat_messages 用于界面展示，不能代替检查点；恢复时依靠请求标识避免重复写消息。

## 9. API 约定

API 前缀为 /api，字段 snake_case，时间为 UTC ISO 8601。成功直接返回业务对象；错误返回 code、message、request_id，不返回内部堆栈。

除注册、登录及无敏感信息的健康检查外，业务接口要求 JWT。个人资源校验归属，公共知识接口仅检查登录。

| 方法与路径 | 输入或用途 |
| --- | --- |
| POST /api/auth/register | JSON：username、password；返回用户公开信息 |
| POST /api/auth/login | JSON：username、password；返回 JWT 和用户公开信息 |
| GET /api/auth/me | 返回当前用户 id、username |
| POST /api/files | multipart：file、purpose（image/knowledge）；分别只接受 JPEG/PNG 或 .md，返回 file_id |
| POST /api/detections | multipart：file 或 file_id 二选一、conf；可选 Idempotency-Key 请求头 |
| GET /api/detections/{id} | 查询任务状态和检测 JSON |
| GET /api/detections/{id}/original | 返回原图文件 |
| GET /api/detections/{id}/image | 返回结果图文件 |
| POST /api/conversations | 创建会话，返回 thread_id |
| GET /api/conversations | 分页查询本人会话 |
| GET /api/conversations/{id}/messages | 分页读取本人消息 |
| POST /api/chat | JSON：thread_id、message、attachment_ids、client_message_id |
| GET /api/documents | 公共文档列表 |
| GET /api/documents/{id}/versions | 公共文档版本列表 |
| GET /api/documents/{id}/versions/{version_id} | 来源及版本内容，供引用与差异展示 |
| GET /api/knowledge/operations/{id} | 本人待确认操作 |
| POST /api/knowledge/operations/{id}/confirm | 确认并继续流程 |
| POST /api/knowledge/operations/{id}/cancel | 取消操作 |
| GET /api/health/ready | 数据库和模型就绪状态 |

检测完成返回 201，仍在执行返回 202；查询接口返回 200。常见错误：401 未登录或令牌失效，404 不存在或无权读取的私有资源，409 版本/幂等冲突或结果未就绪，413 文件过大，422 参数无效，503 服务繁忙或未就绪。

聊天首版使用普通 JSON 响应，包含答案、引用和可选检测任务/待确认操作。闭环稳定后再增加 SSE，不在首批实现流式重连和恢复。

## 10. 前端页面

| 页面 | 内容 |
| --- | --- |
| 注册/登录 | 用户名、密码、错误提示；登录后保存 JWT |
| 图片检测 | 上传、阈值、原图、结果图、目标列表、状态 |
| 智能问答 | 本人会话列表、消息、附件、引用、检测卡片 |
| 知识管理 | 公共文档、版本、来源、上传、差异、确认/取消 |

页面公用当前用户名和退出按钮。退出时清除令牌、用户数据缓存和图片对象 URL。收到 401 统一回到登录页，不能让后一个账号看到前一个账号残留的页面数据。

所有请求走同源 /api，并由请求封装添加 JWT。确认面板展示文档、旧版本和变更摘要，不能只展示一个没有上下文的“确定”按钮。

## 11. Docker 部署

最终只有三个服务：frontend、backend、db。

- frontend：Node 构建，Nginx 运行静态资源并代理 backend:8000，不使用 Vite 开发服务器部署。
- backend：Python 3.11 Linux 镜像，一个 worker，包含 API、Agent 和检测源码；模型权重只读挂载。
- db：固定版本 PostgreSQL + pgvector 镜像，启动准备阶段启用扩展和执行迁移。
- app_storage 命名卷挂载 /app/storage；pg_data 持久化数据库。默认仅前端端口映射到宿主机 localhost。

主要配置：DATABASE_URL、JWT_SECRET、JWT_EXPIRE_MINUTES、MODEL_SOURCE_DIR、MODEL_PATH、STORAGE_ROOT、DEVICE，以及 LLM/Embedding 模型和连接参数。密钥不进入前端和 Git。

WSL 部署副本建议放 Linux 文件系统。Linux 镜像重新安装对应依赖，不复制 Windows Conda 环境或 Windows wheel。数据库健康后启动后端，后端加载模型后 readiness 才通过。

准备权重和 .env 后，交付目标是一条命令启动：

```bash
docker compose up -d --build
```

停止时不加 -v，保留卷数据。明文密码也会进入数据库备份，因此备份同样仅用于本项目的受控环境。

## 12. 开发顺序和验收
